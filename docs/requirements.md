# n8n-insights-viewer 要件定義

- 作成日: 2026-07-07 / 最終更新: 2026-07-10
- ステータス: 方式確定（決定事項は§8、残る未決事項は§9参照）

## 1. 背景・目的

セルフホストのn8n（community edition）では、Insights画面の全機能は使えないが、
その元データはn8nのDBに蓄積されている。このデータを活用し、以下を可視化する
Next.jsアプリケーションを構築する。

1. **Insights**: ワークフローごとの実行数・成功/失敗・実行時間の推移
2. **マシン負荷状況**: n8nが動作するGCEインスタンスのCPU・メモリ・スワップ等の推移
   （背景: 2026-07-04/05にOOMキラーによるn8n停止障害が発生。再発の予兆検知が目的）

## 3. データソース（n8n DB内の利用可能テーブル）

### 3.1 insights_by_period（主データソース）— 2,077行

ワークフロー×期間×メトリクス種別の集計値。**アップグレード不要でここに蓄積済み**。
`insights_raw` は即時compactionされるため常時ほぼ0件であり、参照対象は本テーブル。

| カラム | 意味 |
|---|---|
| metaId | `insights_metadata.metaId` へのFK |
| type | 0=time_saved_min / 1=runtime_ms / 2=success / 3=failure |
| value | 集計値 |
| periodUnit | 0=hour / 1=day / 2=week |
| periodStart | 期間の開始時刻（**UTC**） |

実データの保持状況（n8nのcompaction仕様: hourは90日でdayへ、dayは180日でweekへ集約）:

| periodUnit | 件数 | 期間 |
|---|---|---|
| hour (0) | 1,170 | 2026-04-08 〜 2026-07-07（直近約90日） |
| day (1) | 880 | 2026-01-08 〜 2026-04-07 |
| week (2) | 27 | 2025-12-22 〜 2026-01-05 |

→ **2025-12-22以降、約6.5ヶ月分の実行実績が粒度混在で残っている。**
type=0（time_saved_min）は全て0（ワークフロー側で未設定のため）。

### 3.2 insights_metadata — ワークフロー名の解決

`metaId` → `workflowId` / `workflowName` / `projectName`。
ワークフロー削除後も名前が残る（FKはON DELETE SET NULL）。

### 3.3 execution_entity — 直近7日の実行明細（202行）

`workflowId`, `status`, `mode`, `startedAt`, `stoppedAt`, `createdAt` 等。
**7日/5000件でpruneされるため長期分析には使えない**が、直近の実行一覧・
実行時間分布・失敗の深掘りに使う。

### 3.4 workflow_statistics — 全期間の累計カウンタ（101行）

ワークフロー×イベント名の累計。pruneの影響を受けない生涯累計値。
現在値: production_success 11,965 / production_error 555 / manual_success 1,239 / manual_error 357。

### 3.5 workflow_entity — ワークフローマスタ

`id`, `name`, `active`, `createdAt`, `updatedAt`。一覧表示・アクティブ判定に使用。

## 4. データ取得方式

**大前提: 本番サーバーには一切のソフトウェア導入を行わない。**
サーバー上で使ってよいのはプリインストール済みの標準コマンド（cp, ls, cat等）のみとする。
唯一の例外として、**マシン負荷収集用のスクリプト1本とcron1行の設置のみ許可する**
（2026-07-10ユーザー承認。標準コマンドのみで構成し、新規ソフトは導入しない。§5.3参照）。

### 4.1 方式比較

| 方式 | 内容 | 評価 |
|---|---|---|
| A: DBファイルコピー（**採用・確定**） | サーバー標準コマンド（cp）でスナップショット→`gcloud compute scp`で取得→ローカルで必要テーブルのみ抽出 | **サーバーへの変更ゼロ**。転送は約300MB/回（数分、転送コストは数円）。機微テーブルはローカルで除去 |
| B: サーバー側で抽出エクスポート | sqlite3等をサーバーに導入し必要テーブルのみ出力 | 転送量は小さいが**本番へのソフト導入が必要なため不採用** |
| C: ライブread-only接続 | リモートのSQLiteに直接接続 | SQLiteはネットワーク越し接続不可。SSHFS等は不安定で× |
| D: VM上にAPI追設 | VMに読み取りAPIサーバーを常駐 | e2-microのRAM余力がなくOOM再発リスクを増やすため× |
| E: n8nワークフローでSheets/Driveへプッシュ | n8n自身のワークフローが実行データ・メトリクスを取り出し、Google Sheets/Driveへ定期的に格納 | **不採用（2026-07-10決定）**。理由は§4.2 |

**方式Aを採用する（2026-07-10確定）。** 具体手順（すべてローカルのWindows端末側から実行。サーバーには何も残さない）:

1. `gcloud compute ssh --command` で `database.sqlite` と `-wal` を `/tmp` へ `sudo cp`
   （スナップショット。cpは数秒で完了し、CPU/メモリ負荷はごく小さい）
2. `gcloud compute scp` でローカルの `<repo>/data/raw/` へ取得し、`/tmp` のコピーを削除
3. ローカルで `PRAGMA quick_check` により整合性を確認
   （稼働中DBのファイルコピーはまれに不整合になりうるため。失敗時は再取得）
4. ローカルで必要5テーブル（§3）のみを閲覧用DB `<repo>/data/n8n_insights.sqlite` へ抽出し、
   **生コピー（credentials等を含む）は抽出後に削除**する
5. Next.jsアプリは **ローカルの閲覧用DBのみをread-onlyで参照**（本番DBには一切接続しない）

### 4.2 不採用とした案: n8nワークフローによる取り出し（方式E）— 2026-07-10決定

n8n自身のスケジュールワークフローが実行実績やメトリクスを取り出し、
Google Sheets/Driveへ格納する案を検討したが、**不採用**とした。

**不採用の理由: 取り出す行為自体がn8nに記録され、可視化対象のデータを汚染するため。**

- 収集ワークフローの定期実行（例: 5分間隔なら288回/日）が、そのままn8nの
  実行記録・insights集計・workflow_statisticsにカウントされる。実ワークフローの
  実行数（現状は数十回/日規模）に対して収集実行が支配的になり、
  「n8nの利用実態を見る」という本アプリの目的そのものを損なう
- 「Save execution data: none」設定で実行明細の保存は抑制できるが、
  insights集計はイベントベースで記録されるため汚染は避けられない
- 可視化側で収集ワークフローを除外するルールを設けることも可能だが、
  集計値のあらゆる箇所に除外処理が必要になり、複雑さに見合わない

この決定により、**n8nへのワークフロー追加は一切行わない**（マシン負荷収集を含む。§5参照）。
サーバーからのデータ取得はDBコピー（方式A）に一本化する。

### 4.3 同期頻度・履歴保全

- **同期はBI（Next.jsアプリ）とは別プロセスの手動コマンドとする（2026-07-10決定）**。
  定期実行や、BI起動時の自動実行は行わない（頻繁に見るものではないため不要。
  また起動時実行は起動を遅く・不安定にするため）
  - 実体は独立したCLIスクリプト（npm script例: `npm run sync`）
  - 利便性のため、BIの同期ステータス画面（§6.1-6）から同スクリプトを子プロセスとして
    起動できるボタンを設けてよい（プロセス分離の原則は保つ）
- BIは**手元にあるデータをそのまま表示**する。データが古い・欠けていることに気づいたら、
  ユーザーが同期コマンドで最新を取得する運用（古さの可視化は§6.2参照）
- **未同期期間の警告**: サーバー側の実行明細は7日で消えるため、最終同期から
  6日を超えたらBI画面上で「そろそろ同期しないと実行明細に穴が開く」ことを警告する
- `execution_entity` は7日で消えるため、**同期のたびにローカル側へ追記保存（UPSERT）して7日を超える明細履歴を自前で蓄積する**
  （insights_by_period側は長期保持されるため上書きで良い）
- **同期時に対象テーブルのスキーマを検証する**: n8nは `latest` タグ運用（§8）のため、
  バージョンアップでスキーマが変わりうる。想定スキーマと差異があれば取り込みを中断して
  警告を出し、黙って壊れたデータを蓄積しない

## 5. マシン負荷データの収集

n8nのDBにはマシン負荷情報は存在しないため、新規に収集の仕組みが必要。
ただし以下の2つの制約を守ること。

- §4の大前提: サーバーへのソフト導入・スクリプト配置・cron追加をしない
- §4.2の決定: n8nへのワークフロー追加もしない（収集実行がinsights等に記録され、データを汚染するため）

### 5.1 方式比較

| 方式 | 内容 | 評価 |
|---|---|---|
| A: n8nワークフローで収集し Data Table / Sheets に保存 | Schedule Trigger + Execute Command | **不採用（2026-07-10）**。§4.2と同じ理由（収集実行自体がn8nに記録されデータを汚染する） |
| B: 同期時のスポット収集（**採用**） | 同期コマンド（§4.3）の実行時に、SSHで `/proc/meminfo` 等を1回取得し、ローカルに記録 | **サーバー変更ゼロ・常駐なし**。連続的な推移は取れず、同期した時点のサンプルのみになる |
| C: GCP Cloud Monitoring API（補完） | エージェントレスのメトリクスをAPIで取得 | サーバー変更ゼロ。**メモリ・スワップはOps Agentが必要**（RAM消費のため導入不可）だが、**CPU使用率は24時間連続・過去6週間まで取得可能**。連続データはこれで補う |
| D: VM上のcronで定期ファイル出力（**採用**） | 1時間に1回、標準コマンドでメモリ等を1行ファイルに追記し、同期時に回収 | メモリの連続データが取れる唯一の現実解。「何も置かない」原則の明示的な例外としてユーザー承認済み（§5.3） |
| 参考: 既存ログの流用 | syslog等から定期的なメモリ値を読む | **不可**。定期的なメモリ値を記録する仕組みはデフォルトで存在しない（sysstat等は未導入で、導入は原則違反）。ただしOOMイベントの記録には使える（下記） |

**方式B・C・Dを組み合わせて採用する（2026-07-10確定）。**役割分担:

- **方式D（主）**: メモリ等の連続データを1時間粒度で蓄積（§5.3）
- **方式B**: 同期時に最新のスポット値を取得し、あわせてOOMログ・方式Dの出力ファイルを回収
- **方式C（補完）**: CPU使用率の連続データ（過去6週間まで遡れる。方式D設置前の期間や
  cron停止期間の補完にも使う）

Windows端末からの定期的なSSHポーリングは行わない（頻繁に見るものではないため不要と判断）。

方式Bの内容（すべて同期コマンドの一部として実行。SSH取得は1コマンドにまとめる）:

- 収集項目: MemAvailable / MemFree / SwapTotal / SwapFree（`/proc/meminfo`）、
  load average（`/proc/loadavg`）、`docker stats --no-stream` によるコンテナ別CPU/メモリ、
  `database.sqlite` + WALのファイルサイズ、ルートFSの空き
- **OOMイベントの回収**: カーネルログからOOM記録を読み取る。読み取り元は `dmesg` ではなく
  **永続化されたログ（`journalctl -k` または `/var/log/kern.log*`）**とする。
  dmesgは再起動で消えるが、永続ログなら**再起動をまたいでも**同期していなかった期間の
  OOMを後から検知できる（VM再起動を伴う障害こそ見逃せないため）
- **CPU使用率の回収**: GCP Monitoring APIから前回同期以降のCPU使用率を取得
  （過去6週間まで遡れるため、同期間隔が空いても連続データを維持できる）
- 保存先: ローカルのSQLite（§4.3の蓄積DBと同じ場所）に追記

### 5.2 制約

- 過去に遡ってのメモリ系データは存在しない。**方式D設置日以降のみ**1時間粒度の連続データが
  得られる（設置前の期間はCPU使用率のみ方式Cで遡って補完可能）
- サンプルがない区間（設置前・cron停止中）は欠測としてグラフ上に明示する（ゼロや補間で埋めない）

### 5.3 VM上の定期ファイル出力（方式D）— 採用（2026-07-10決定）

VM上のcronで1時間に1回、メトリクスをファイルへ追記し、同期時に回収する。
「サーバーに何も置かない」原則（§4大前提）の**明示的な例外としてユーザーが承認済み**
（同原則の発端はDB読み取り用クライアント（sqlite3）を無断導入した件への指摘であり、
標準コマンドのみで構成される本収集スクリプトは趣旨が異なる、との判断）。

**管轄: 収集スクリプトの作成・設置・管理も本リポジトリの「DB取得機能」の一部とする。**
出力ファイルを読むのが本リポジトリだけである以上、形式の定義と生成を同じ場所で
管理するのが合理的なため（当初の「リポジトリ範疇外」の整理は撤回された）。

設計・条件:

- **新規ソフトは導入しない**: cron 1行 + プリインストール済みの標準コマンド
  （`cat /proc/meminfo`, `cat /proc/loadavg`, `docker stats --no-stream`, `du` 等）のみで構成する
- **n8nに一切関与しない**: n8nの外（ホストのcron）で動くため、実行記録・insightsを
  汚染しない（§4.2の不採用理由に抵触しない）
- サーバー上のフットプリントを最小に固定する: **専用ディレクトリ1つ**（例: `/root/insights_collector/`）
  に**スクリプト1本 + 出力ファイル**のみ。cronはrootのcrontabに**1行**
  （毎時。分は00を避けてずらし、ワークフローのスケジュール実行と重ねない）
- 負荷: 実行時間1秒未満、常駐なし。追記量は1行150バイト程度 → **年間約1.3MB**
  （ローテーション不要の規模。肥大が気になれば月次ファイル分割を後日検討）
- 出力形式: CSVまたはJSONL、UTCタイムスタンプ、項目は§5.1方式Bと同一。
  スクリプト内に**バージョン識別子**を持たせ、出力にも記録する
  （リポジトリ側の想定とサーバー上の設置版のズレを同期時に検知するため）
- **設置・更新は本リポジトリのセットアップコマンドで行う**（例: `npm run deploy-collector`）。
  実行前に「サーバーへ何を配置し、crontabに何を追加するか」を表示し、
  ユーザーが内容を確認してから実行する。勝手に（暗黙に）設置・更新しない
- 1時間粒度の妥当性: OOMの予兆（MemAvailableの数時間〜数日単位の漸減）の検知には十分。
  分単位のスパイクは捉えられないが、それはOOMログの回収（§5.1）で事後検知できる
- 設置前の期間・cron停止期間は欠測となる（CPUのみ方式Cで補完可能）

## 6. アプリケーション要件（Next.js）

### 6.1 画面・機能

| # | 画面 | 内容 |
|---|---|---|
| 1 | ダッシュボード | 直近7日/30日のサマリ: 総実行数、成功率、失敗数、総実行時間、直近のマシン負荷スパークライン、**現在の状態バッジ（§6.3）** |
| 2 | Insights推移 | 実行数・成功/失敗・実行時間の時系列グラフ。粒度（hour/day/week）切替、期間指定、ワークフロー絞り込み |
| 3 | ワークフロー別一覧 | ワークフローごとの実行数・成功率・平均/合計実行時間・累計値（workflow_statistics）。ソート・アクティブ絞り込み |
| 4 | 実行明細 | ローカル蓄積した execution_entity の一覧（状態・モード・所要時間）。失敗のみ表示等のフィルタ |
| 5 | マシン負荷 | メモリ（available/swap）・CPU load・コンテナ別使用量・DBサイズの時系列。OOMイベントのマーカー表示 |
| 6 | 同期ステータス | 最終同期日時、データのカバー範囲、取り込み件数、未同期期間の警告（§4.3）、同期スクリプトの起動ボタン |

### 6.2 表示上の注意

- **時間軸の表示範囲はBIを起動した日（今日）まで**とする（2026-07-10決定）。
  データの末尾が今日より前なら、そこから今日までを空白のまま見せることで
  「データが古い」ことが一目でわかるようにする。データ末尾には
  「データはここまで（最終同期: ○月○日 ○時）」の注記を出し、§6.1-6の同期実行へ誘導する
- DB内の日時はすべてUTC。**表示・集計はJST（Asia/Tokyo）に変換する（2026-07-10決定）**
- 日次集計の区切りに注意: hourlyデータが残っている期間（直近約90日）はJSTの0時区切りで
  正しく日次集計できるが、それ以前はn8nがUTC区切りで日次集約済みのため、
  JSTの1日とは最大9時間ズレる。古い期間はUTC区切りの近似値である旨を画面上に注記する
- insights_by_period は期間により粒度が異なる（hour→day→week）ため、
  長期間表示時は粒度の混在を吸収する（dayに正規化する等）
- type=0（time_saved_min）は現状データなしのため表示対象外（データが入り始めたら表示）

### 6.3 状態評価 — 予兆の可視化（2026-07-10決定）

外部への通知・アラートは**行わない**。代わりに、画面を開けば
「良くない状態（OOM再発等）に近づいているか」が一目でわかること。

- **状態レベル**: 最新の収集値から「正常 / 注意 / 危険」の3段階を判定し、
  ダッシュボードにバッジ表示する。判定根拠（どの指標がどの閾値を超えたか）も併記する
- **閾値の参照線**: マシン負荷のチャートに注意/危険の閾値線を描画する。既定値
  （2026-07のOOM障害の実測に基づく。設定ファイルで変更可能とする）:
  - MemAvailable: 注意 150MB / 危険 100MB（OOM未発生で耐えた最低実績は58MB）
  - スワップ使用量: 注意 1GB / 危険 1.5GB（2GB中。ピーク実績468MB）
  - database.sqlite + WAL サイズ: 注意 400MB（障害時294MBで肥大が一因だった）
- **実績マーカー**: 過去のOOM発生時刻（dmesgから回収したもの）をチャート上に
  マーカー表示し、現在値と「実際に落ちたときの水準」を比較できるようにする
- **トレンド表示**: OOMの予兆はMemAvailableの漸減として現れるため、
  直近のサンプル系列から傾き（増加/横ばい/減少）を算出して主要指標に添えて表示する。
  DBサイズの増加傾向も同様に表示する。メモリ系は同期時のスポットサンプル（§5）のため、
  サンプル数が少ない場合は「参考値」であることを明示する

### 6.4 技術構成

- Next.js（App Router）+ TypeScript
- データアクセス: better-sqlite3（ローカルの閲覧用DBをread-only openする）
- グラフ: 軽量なチャートライブラリ（Recharts等）
- 実行形態: **この端末（Windows 11）上で `npm run dev` / `npm start` で起動して閲覧する（2026-07-10決定）**。
  デプロイはしない。同期・収集スクリプトもWindows上で動作すること（gcloud CLI利用）

## 7. 非機能要件

| 項目 | 要件 |
|---|---|
| 本番影響 | **サーバーへのソフトウェア導入・常駐プロセス追加・n8nへのワークフロー追加を行わない**（§4.2）。サーバー上での操作は標準コマンドによる読み取り（cat/cp/ls等）とscpによるファイル取得、および**ユーザー承認済みの例外である負荷収集スクリプト1本+cron1行の設置**（§5.3、設置内容を表示して確認のうえ実行）のみ |
| セキュリティ | 生コピーに含まれる credentials_entity 等の機微テーブルは、閲覧用DBへの抽出後に**生コピーごと削除**する。`data/` ディレクトリ全体を `.gitignore` に追加しコミットしない |
| コスト | GCPコスト増ゼロ（追加リソースなし。転送量も数MB/回で無視できる） |
| データ保全 | execution_entity とマシン負荷はローカルに追記蓄積し、prune/ローテーションで消えても手元に履歴が残ること |

## 8. 決定事項（2026-07-10）

| 論点 | 決定 | 理由 |
|---|---|---|
| データ取得方式 | **DBコピー（§4方式A）に一本化**し、この端末（Windows）にコピーして利用する | n8nワークフローで取り出す案（方式E）は、取り出す行為自体がn8nの実行記録・insights集計に記録され、可視化対象のデータを汚染するため不採用 |
| マシン負荷収集 | Windows端末からのSSHポーリング + GCP Monitoring（CPU）補完（§5方式B+C） | 同上の理由でn8nワークフロー収集も不採用。夜間（PC停止中）の欠測は許容する |
| 開発の順序 | **アプリ開発を先行**し、負荷収集の常時稼働は後からでよい | 負荷監視はそれほどシビアな要件ではなく、収集開始遅れによる欠測は許容できる |
| n8nイメージ | `latest` タグ運用を継続する（バージョン固定しない） | シビアな要件ではなく、バージョン固定は更新作業の手間が増える。スキーマ変更リスクは§4.3のスキーマ検証で検知して都度対応する |
| タイムゾーン | **JST（Asia/Tokyo）に変換して表示・集計**する（§6.2） | 利用者は日本時間で運用しているため |
| アプリ実行環境 | この端末（Windows 11）上でローカル実行。デプロイしない | — |
| アラート | **外部通知は行わない**。代わりに画面上の状態バッジ・閾値線・トレンド表示で「良くない状態への接近」を可視化する（§6.3） | 個人運用でありアプリを開いたときに気づければ十分 |
| 同期・収集の起動方式 | **BIとは別プロセスの手動コマンドとする**（§4.3）。定期実行・BI起動時の自動実行はどちらも行わない。BIは手元データを今日までの時間軸で表示し、古さが見えたらユーザーが同期を実行する（§6.2） | 頻繁に見るものではないため定期収集は過剰。起動時の自動取得は起動を遅く・不安定にする（300MB転送・要ネットワーク/認証） |
| マシン負荷の連続収集 | **VM上のcronによる1時間ごとのファイル出力（§5.3方式D）を採用**し、スクリプトの作成・設置・管理も本リポジトリの「DB取得機能」に含める | 「何も置かない」原則の発端はDBクライアント（sqlite3）の無断導入への指摘であり、標準コマンドのみのスクリプト1本+cron1行は明示的な例外として承認。出力ファイルを読むのが本リポジトリだけなので、形式定義と生成を同じ場所で管理するのが合理的 |
